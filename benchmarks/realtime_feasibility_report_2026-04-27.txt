一、問題定義
============

本系統使用 Arducam B0332（OV9281）全域快門相機以 120 fps 擷取影像，
經影像處理管線偵測壓電馬達位置與姿態後，透過 Keysight 33622A 函數產生器
發送 SCPI 指令控制驅動波形。

相機每 8.33 ms 產生一幀影像。若要實現即時閉迴路控制，系統必須在每一幀的
8.33 ms 時間預算內完成所有處理，否則將產生幀堆積、掉幀、或控制延遲，
導致控制品質下降。

本報告的核心問題是：

    「系統能否在 8.33 ms 的時間預算內完成影像處理與控制指令輸出，
      以維持 120 fps 即時吞吐量？」


二、系統架構
============

系統採用三級流水線（Three-Stage Pipeline）多執行緒架構：

    ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
    │ Stage 1      │     │ Stage 2      │     │ Stage 3      │
    │ Capture      │────>│ Process      │────>│ Main Thread  │
    │ Thread       │     │ Thread       │     │ + FG Control │
    └──────────────┘     └──────────────┘     └──────────────┘
     cap.read()           undistort            cv2.imshow()
     frame_queue.put()    rotate + flip        PID 計算
                          HSV mask             FG SCPI 指令
                          morphology           (每 5 幀一次)
                          contour detect
                          Kalman filter
                          EMA smooth
                          result_queue.put()

各級透過 queue.Queue 進行資料傳遞：
  - frame_queue：Capture Thread → Process Thread（容量 120 幀）
  - result_queue：Process Thread → Main Thread（容量 30 幀）

硬體配置：
  - 相機：Arducam B0332, OV9281 sensor, 640x480, MJPG, DirectShow, 120 fps
  - 函數產生器：Keysight 33622A, USB-TMC (PyVISA), SCPI 控制
  - 畸變校正：TPS (Thin Plate Spline) 預計算映射表, cv2.remap()
  - 校正後輸出尺寸：462x314 px


三、流水線即時性的判定準則
==========================

流水線架構的關鍵特性是：各級平行執行、同時處理不同幀。

                    0     8.33   16.67  25.00  33.33  41.67  ms
                    ├──────┼──────┼──────┼──────┼──────┤
    Capture:        [F1]   [F2]   [F3]   [F4]   [F5]   ...
    Process:          [F1]   [F2]   [F3]   [F4]   ...
    Main:               [F1]   [F2]   [F3]   [F4] ...

因此，即時性的判定準則不是「所有步驟加總 < 8.33 ms」，而是：

    「每一級的單幀處理時間是否都 < 8.33 ms？」

只要每一級都在 8.33 ms 內完成當前幀的處理，pipeline 就不會堆積，
系統吞吐量就能維持在 120 fps。

需要注意的是，end-to-end latency（一幀從進入到完成的總延遲）
在流水線架構中自然會是各級之和（數 ms 到數十 ms），這不影響吞吐量，
只影響控制的響應延遲。對於本系統中慣性較大的壓電馬達而言，
數 ms 等級的管線延遲在機械響應時間常數之內，不構成控制瓶頸。


四、測試方法
============

本報告包含四項獨立測試，從不同角度驗證系統即時性。


【測試 A】函數產生器模式切換時間
─────────────────────────────────
目的：量測兩代 FG 切換實作的 SCPI 指令序列耗時

方法：
  - 計時工具：time.perf_counter()（Windows 下解析度 < 1 us）
  - 計時範圍：第一個 inst.write() 前 → 最後一個 inst.write() 後
  - 每個情境重複 50 次
  - 兩代實作之間以 *RST 完全重置儀器
  - 每個情境結束後發送 OUTP OFF 確保安全

  第一代（dual_modal_selector_4modes.py）：
    每次切換完整流程：關輸出 → 讀 CSV 檔 → 上傳波形(write_binary_values)
    → 設定 ARB 參數 → 設定 Track/Sync → 設定極性 → 開輸出

  第二代（dual_modal_4ms.py）：
    啟動時一次性預載所有波形，切換時依條件分支：
    - 同組（Mode 1↔3 或 2↔4）：僅切換輸出極性（3 條 SCPI）
    - 跨組（Mode 1/3↔2/4）：切換波形名稱 + 採樣率 + 頻率 + 極性（10 條 SCPI）
    - 待機啟動（None→任意）：完整參數設定

  腳本：benchmarks/fg_switching_benchmark.py


【測試 B】Process Thread 單幀處理時間
──────────────────────────────────────
目的：分解量測影像處理管線各子步驟耗時

方法：
  - 計時工具：time.perf_counter()
  - 暖機 50 幀後開始記錄，量測 500 幀
  - 在每個子步驟前後插入計時點
  - 提供兩種模式：
    offline（隨機合成幀，純測處理速度）
    online（實際相機幀，含真實影像內容）
  - 子步驟分解：Undistort → Rotate/Flip → Kalman Predict
    → HSV+Morphology+Contour → Kalman Correct → EMA+Angle → Draw Overlay

  腳本：benchmarks/process_thread_benchmark.py


【測試 C】系統端對端延遲（方法 A：軟體時間戳記）
─────────────────────────────────────────────────
目的：量測一幀從相機抵達到 FG 指令送出的完整延遲鏈

方法：
  - 在四個關鍵位置植入 time.perf_counter() 時間戳記：
    T_capture      ：cap.read() 成功後
    T_queue_in     ：frame_queue.put() 後
    T_process_done ：result_queue.put() 後
    T_fg_sent      ：inst.write() 後
  - time.perf_counter() 為 OS 層級單調時鐘，跨執行緒可直接相減
  - 時間戳記透過 queue 資料結構跨執行緒傳遞
  - 暖機 100 幀後量測 500 幀
  - 延遲分量定義：
    seg1 = T_queue_in - T_capture（Capture Thread 內部）
    seg2 = T_process_done - T_queue_in（Process Thread + queue 等待）
    seg3 = T_fg_sent - T_process_done（Main Thread 反應 + FG 指令）
    total = T_fg_sent - T_capture（端對端總延遲）

  注意：此測試中每幀都發送 FG 指令（120 SCPI/sec），
  不代表實際系統行為，目的是壓力測試 USB-TMC 匯流排。

  腳本：benchmarks/latency_benchmark.py


【測試 D】流水線吞吐量驗證（核心測試）
───────────────────────────────────────
目的：在實際運作條件下驗證三級流水線是否維持 120 fps 零掉幀

方法：
  - 完整啟動三執行緒系統 + Keysight 33622A
  - FG 指令頻率：每 5 幀一次（24 Hz），與實際 PID 控制一致
  - 暖機 100 幀後量測 1000 幀
  - 分別計時各級處理時間：
    Stage 1：cap.read() 到 frame_queue.put() 的耗時
    Stage 2：Process Thread 從取幀到放結果的純處理時間
    Stage 3a：Main Thread 無 FG 指令時的反應時間
    Stage 3b：Main Thread 含 FG 指令時的反應時間
  - 同時量測：
    幀間隔（frame interval）：驗證 Main Thread 端的實際吞吐量
    掉幀率（drop rate）：frame_queue 滿時丟棄的幀數比例
  - 判定準則：每一級 p99 < 8.33 ms 且掉幀率 = 0%

  腳本：benchmarks/pipeline_throughput_benchmark.py

六、分析與討論
==============

6.1  為什麼流水線架構使即時控制可行
───────────────────────────────────

若採用單執行緒序列架構，所有步驟必須在 8.33 ms 內完成：

  擷取(~0.03) + 處理(~2.56) + 顯示 + PID + FG指令(~1.20) = ~3.8 ms（不含顯示）

即使序列架構理論上也足夠，但 cv2.imshow() 和 Windows 視窗事件處理的耗時
具有高度不確定性（數 ms 到數十 ms），極易導致掉幀。

三級流水線架構將各步驟解耦至獨立執行緒，優點如下：
  (a) 各級平行執行，任何一級的偶發延遲不阻塞其他級
  (b) frame_queue 提供緩衝，吸收 Capture 與 Process 之間的速率波動
  (c) FG 指令在 Main Thread 發送，不阻塞 Process Thread 的影像處理
  (d) cv2.imshow() 的不確定延遲被隔離在 Main Thread，不影響擷取與處理


6.2  瓶頸分析
─────────────

系統目前的瓶頸是 Process Thread（2.56 ms mean），其中兩大子步驟佔 82%：
  - HSV + Morphology + Contour Detection：1.14 ms（45%）
  - Undistort (TPS remap)：0.94 ms（37%）

Process Thread 的 p99 = 4.38 ms，距離 8.33 ms 預算仍有 3.95 ms 餘裕（47%），
代表即使未來需要增加更複雜的影像處理步驟（例如多目標偵測、更高解析度），
仍有充足的擴展空間。


6.3  FG 指令的偶發延遲
──────────────────────

FG 指令（set_voltages, 2 條 SCPI write）的 mean = 1.19 ms，但 max = 48.46 ms。
此極端值為 USB-TMC 匯流排在 Windows 作業系統下的非確定性延遲，成因包括：
  - USB 匯流排仲裁延遲
  - Windows 核心層級的中斷處理延遲
  - USB hub 或 driver 的偶發重傳

此延遲不影響系統吞吐量，原因如下：
  (a) FG 指令在 Main Thread 發送，與 Capture/Process Thread 完全平行
  (b) FG 指令頻率為 24 Hz（每 5 幀一次），即使某次指令耗時 48 ms，
      也僅影響該次控制更新，不會造成掉幀
  (c) 從 pipeline 吞吐量實測結果（120.7 fps, 0% drop）可證實
      此偶發延遲未影響系統整體即時性


6.4  端對端延遲 vs. 吞吐量的區分
─────────────────────────────────

端對端延遲（end-to-end latency）是指單一幀從相機擷取到控制指令送出的
總經過時間。在流水線架構中，此延遲約為各級之和（約 4~5 ms 不含 FG 指令），
加上 FG 指令時約 5~6 ms。

吞吐量（throughput）是指系統每秒能處理多少幀。由於三級平行執行，
吞吐量取決於最慢那一級（Process Thread, 2.56 ms），
理論最大吞吐量 = 1000 / 2.56 = 390 fps，遠超 120 fps 需求。

對於壓電超聲波馬達控制而言，重要的是吞吐量而非端對端延遲：
  - 馬達的機械響應時間常數遠大於 5 ms 的管線延遲
  - 只要吞吐量維持 120 fps，控制器每 8.33 ms 就能獲得新的位置回授
  - 管線延遲是固定的、可預測的，PID 控制器可據此調整參數


七、結論
========

本報告透過四項獨立測試，從子步驟分解、模組計時、壓力測試、以及
實際運作條件等不同角度，全面驗證了系統的即時性能。核心結論如下：

  1. 三級流水線的每一級處理時間均遠低於 8.33 ms 的時間預算：
     - Capture Thread：0.03 ms（使用 0.4% 預算）
     - Process Thread：2.56 ms（使用 31% 預算，69% 餘裕）
     - Main Thread + FG：1.20 ms（使用 14% 預算，p99 = 2.04 ms）

  2. 系統實測吞吐量 120.7 fps，掉幀率 0.0%，完全滿足 120 fps 即時需求。

  3. 第二代 FG 切換策略（預載波形 + 極性/波形組快速切換）相比第一代
     實現了 13.7 倍加速，同組切換可在 2 ms 內完成。

  4. 影像處理管線仍有 69% 的時間餘裕，為未來增加更複雜的處理步驟
    （如多目標追蹤、更高解析度影像）預留了充足的擴展空間。

本系統的多執行緒流水線架構經驗證可實現 120 fps 即時視覺伺服控制，
滿足壓電超聲波馬達閉迴路驅動的即時性要求。

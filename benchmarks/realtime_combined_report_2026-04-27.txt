  即時性組合驗證報告

  測試日期：2026-04-27

一、問題與疑慮
==============

相機以 120 fps 運行，每幀時間預算為 8.33 ms。
函數產生器（FG）模式切換的 SCPI 指令耗時遠超此預算：

  同組切換（極性）：mean = 8.2 ms，max = 36.4 ms
  跨組切換（波形）：mean = 7.7 ms，max = 11.4 ms
  電壓微調：        mean = 1.2 ms，max = 48.5 ms（偶發 USB 延遲）

若「影像處理 + FG 指令」序列執行，加總後必定超過 8.33 ms。
問題是：這是否意味著系統無法即時控制？


二、回答：不會，因為兩者平行執行
================================

本系統採用三執行緒流水線架構，影像處理與 FG 指令分屬不同執行緒：

  Capture Thread  ──→  Process Thread  ──→  Main Thread
   (讀取相機幀)         (影像處理)            (顯示 + PID + FG 指令)

Process Thread 和 Main Thread 透過 result_queue 解耦。
Process Thread 將處理結果放入 queue 後立刻處理下一幀，
完全不等待 Main Thread 是否已消費上一筆結果、也不等待 FG 指令完成。

因此，正確的即時性判定準則是：

  ┌────────────────────────────────────────────────────────────┐
  │  每一級的單幀處理時間 < 8.33 ms                           │
  │  （而非所有步驟加總 < 8.33 ms）                            │
  └────────────────────────────────────────────────────────────┘


三、驗證方法
============

為回答此問題，執行了三項測試：


【測試 1】組合延遲測試（序列加總，最差情境）
────────────────────────────────────────────

方法：
  在同一個執行緒上，對每一幀先做完整影像處理，再立刻發送 FG 指令，
  量測兩者加總時間。5 輪 × 200 幀 = 1000 幀/情境。

  此測試模擬「假如沒有多執行緒」的最差情境。

結果：

  情境               Process   FG 指令    Combined   超出預算比例
  ─────────────────  ────────  ─────────  ─────────  ──────────
  A. 電壓微調         2.54 ms   20.35 ms   22.89 ms   46.3%
  B. 同組切換(1↔3)    2.71 ms   26.70 ms   29.41 ms   76.0%
  C. 跨組切換(1↔2)    2.48 ms  144.93 ms  147.41 ms   98.8%
  D. 純影像處理        2.43 ms       —       2.43 ms    0.0%

  Round 間一致性（Combined mean 的跨輪標準差）：
    A: std = 6.02 ms
    B: std = 0.34 ms
    C: std = 1.20 ms
    D: std = 0.11 ms

結論：
  若序列執行，A/B/C 三個情境全部超出 8.33 ms 預算。
  但 D（純影像處理）穩定在 2.43 ms，遠低於預算。
  這證明了瓶頸在 FG 指令的 USB-TMC 通訊，而非影像處理管線。


【測試 2】流水線吞吐量驗證（實際多執行緒架構）
──────────────────────────────────────────────

方法：
  啟動完整三執行緒系統，FG 指令每 5 幀發送一次（24 Hz），
  與實際 PID 控制行為一致。暖機 100 幀後量測 1000 幀。
  分別計時各級的處理時間。

結果：

  Pipeline Stage                    mean     p99      max     < 8.33 ms?
  ────────────────────────────── ──────── ──────── ──────── ──────────
  Capture Thread (讀幀+入隊)     0.031 ms  0.067 ms  0.239 ms   PASS
  Process Thread (影像處理)      2.56 ms   4.38 ms   7.12 ms   PASS
  Main Thread (無 FG 指令)       0.005 ms      —     0.038 ms   PASS
  Main Thread (含 FG 指令)       1.20 ms   2.04 ms  48.46 ms   PASS(p99)

  系統吞吐量：120.7 fps
  掉幀率：0.0%（1101 幀全部處理，零丟棄）

結論：
  在真正的多執行緒架構下，每一級都在 8.33 ms 以內完成。
  即使 Main Thread 偶爾被 FG 指令阻塞 48 ms，
  Process Thread 和 Capture Thread 完全不受影響，持續處理。


【測試 3】模式切換期間 Process Thread 是否受影響
────────────────────────────────────────────────

方法：
  啟動完整三執行緒系統，每 50 幀在 Main Thread 觸發一次 FG 模式切換
  （交替進行同組切換與跨組切換，共 20 次）。
  記錄每一幀 Process Thread 的處理時間，
  比較「模式切換期間」與「非切換期間」的統計差異。

結果：

  Process Thread 計時         幀數     mean      std      p95      max
  ─────────────────────────  ──────  ────────  ───────  ───────  ───────
  全部幀                      1002    2.75 ms   0.68 ms  3.74 ms  4.66 ms
  模式切換期間（±50ms 窗口）   124    2.80 ms   0.70 ms  3.83 ms  4.66 ms
  非切換期間                   878    2.75 ms   0.68 ms  3.74 ms  4.64 ms

  差異：0.05 ms（1.9%），統計上無顯著差異。

  FG 模式切換時間（同時量測）：
    同組切換：mean = 8.2 ms, max = 36.4 ms
    跨組切換：mean = 7.7 ms, max = 11.4 ms

  系統吞吐量：120.6 fps
  掉幀率：0.0%
  超過 8.33 ms 預算的幀數：0/1002（0.0%）

結論：
  即使 FG 模式切換在 Main Thread 耗時 8-36 ms，
  Process Thread 的處理時間完全不受影響（差異僅 0.05 ms）。
  兩者在獨立執行緒上運行，無共享阻塞。


四、為什麼 FG 切換超過 8.33 ms 不影響即時性
============================================

以具體時間軸說明：

  假設在第 250 幀時，Main Thread 發起跨組模式切換（耗時 ~10 ms）：

  時間(ms)    0     8.33   16.67   25.00   33.33
              ├──────┼──────┼───────┼───────┤
  Capture:    [F250] [F251] [F252]  [F253]  [F254]     ← 持續讀幀，不受影響
  Process:    [F249] [F250] [F251]  [F252]  [F253]     ← 持續處理，不受影響
  Main:       [F249 ──── FG切換 10ms ────][F250][F251]  ← 被阻塞 10ms

  在 Main Thread 被 FG 切換阻塞的 10 ms 期間：
  - Capture Thread 照常以 120 fps 讀幀，放入 frame_queue
  - Process Thread 照常從 frame_queue 取幀並處理，放入 result_queue
  - result_queue 會暫時累積 1~2 幀的結果（queue 容量 30，完全足夠）
  - Main Thread 恢復後，立刻消費累積的結果，不掉幀

  這就是流水線架構的優勢：各級獨立運行，queue 提供緩衝。

  極端情況：即使 FG 切換耗時 150 ms（跨組最差情境），
  Capture 和 Process 仍照常工作，result_queue 會累積約 18 幀結果。
  Main Thread 恢復後快速消費這些結果，吞吐量瞬間回復正常。
  唯一的代價是這 150 ms 期間沒有新的控制指令輸出——
  但壓電馬達會在最後一次設定的波形下持續運行，不會停止。

六、結論
========

1. 影像處理管線（Process Thread）的 p99 = 4.38 ms，
   僅佔 8.33 ms 預算的 53%，遠低於即時性門檻。

2. FG 模式切換（8-36 ms）雖然超過單幀預算，但在獨立的 Main Thread 上執行，
   實測證明對 Process Thread 處理時間的影響僅 0.05 ms（1.9%），無統計顯著差異。

3. 在觸發 20 次模式切換（含同組與跨組）的壓力測試下，
   系統全程維持 120.6 fps，零掉幀。

4. FG 模式切換期間，馬達在最後設定的波形下持續運行，
   不會因為切換延遲而停止驅動。切換完成後新的控制指令立即生效。

5. 綜上，本系統的三執行緒流水線架構有效地將 FG 通訊延遲與影像處理解耦，
   驗證了 120 fps 即時視覺伺服控制的可行性。
